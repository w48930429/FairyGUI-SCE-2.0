# 后续功能模块补充

## 目标

将 AutoArmy 从“可玩原型”推进到“可持续迭代的内测版本”，明确后续模块优先级、阶段边界与验收口径。

## 当前基线

- 已有服务端权威战斗、关卡结算、进度存储与身份迁移。
- 已有客户端战场渲染与基础交互 HUD。
- 已有共享层单元测试与双端构建链路。

## 模块优先级

### P0（必须优先）

- 编队系统：固定阵容改为可配置阵容/站位/兵种选择。
- 数据驱动配置：关卡、敌人、奖励、成长数值从代码迁移到配置。
- 持久化后端升级：从本地文件仓储迁移到 CloudData/DB（含迁移策略）。

### P1（核心增强）

- 会话与并发健壮性：重连恢复、会话过期清理、并发隔离。
- 经济与养成扩展：多资源、成长线与章节解锁节奏。
- 内容扩展：章节、Boss、敌方技能/行为多样化。

### P2（体验与运营）

- 客户端表现增强：技能特效、打击反馈、音频与结算表现。
- 测试体系升级：集成测试、E2E、多人并发回归。
- 观测与调优：日志埋点、错误监控、平衡性指标看板。

## 阶段里程碑

### M1：可配置战斗准备（建议 1-2 个迭代）

- 交付编队数据模型与服务端校验。
- 客户端提供最小可用编队 UI（按钮/槽位方式，非拖拽）。
- 开战时使用玩家编队，不再依赖固定 ally 阵容。

### M2：稳定存储与内容扩展（建议 2-3 个迭代）

- 接入正式存储后端并完成历史数据迁移。
- 完成第一批章节/关卡扩展与数值分层。
- 完成会话异常与重连恢复主路径。

### M3：内测就绪（建议 2 个迭代）

- 关键流程 E2E 全通过（选服 -> 编队 -> 开战 -> 结算 -> 升级）。
- 客户端体验与反馈达到可用标准。
- 运营观测指标可追踪核心行为与异常。

## 验收口径（跨阶段）

- 文档先行：每个模块开工前必须有 change proposal 与 tasks。
- 边界明确：服务端权威，客户端展示与输入，Shared 只放协议与模型。
- 验证闭环：每次 change 至少补一条可复现验证记录。
- 构建门禁：`Server-Debug`、`Client-Debug` 必须通过。
